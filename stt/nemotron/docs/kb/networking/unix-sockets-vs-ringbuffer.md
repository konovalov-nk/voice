# Unix Sockets vs Ring Buffer

## Проблема

Можно ли использовать Unix socket как буфер: если никто не читает, данные остаются?

## Ответ: нет

Unix stream socket — это **канал связи**, а не хранилище. Буфер в ядре — это ~16-128KB (конфигурируется через `net.core.wmem_default` / `SO_SNDBUF`). Когда буфер заполняется:

- **blocking send**: писатель блокируется
- **non-blocking send**: `EAGAIN` / `EWOULDBLOCK` — данные теряются

Т.е. если клиент отключился или не читает, новые данные просто некуда писать.

## Как сделано в сервисе

```
┌─────────────────────┐
│   tokio::broadcast  │  ← 256 слотов, in-memory
│   ring buffer       │
└────────┬────────────┘
         │
         ├──► Client A (читает)       ← получает все
         ├──► Client B (не читает)    ← отваливается по lag
         └──► (никто не подключен)    ← broadcast без receiver
                                       данные не теряются (буфер внутри tx)
```

**Если клиентов нет** — сообщения просто хранятся в broadcast-буфере (256 последних). Когда клиент подключается, он получает **начиная с самого нового** (не пропуская ничего).

**Если нужна история между запусками** — пишем рядом лог-файл.

## Когда сокет — правильный выбор

- Данные идут **live** от одного producer к N consumer
- Задержка важнее гарантии доставки
- Consumer может отвалиться и переподключиться

## Когда нужен не сокет

- Нужно хранить историю между рестартами → **файл + tail -f**
- Нужно гарантировать exactly-once delivery → **message queue** (NATS, RabbitMQ)
- Нужен двусторонний RPC → **gRPC**
